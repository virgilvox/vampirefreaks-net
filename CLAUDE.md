# CLAUDE.md

## Non-negotiable rules

These apply to every project, every file, every commit. They override everything below.

### Git authorship

Never add Claude, any AI assistant, or any tool as an author, co-author, or contributor. Anywhere. No `Co-Authored-By` trailers, no `Signed-off-by`, no "generated by" lines, no AI attribution in commit messages, code comments, file headers, changelogs, or PR descriptions. Every commit reads as if the human developer wrote all of it, because they are accountable for all of it.

### Voice and prose

This covers everything with words in it: READMEs, docs, code comments, commit bodies, PR descriptions, issue text, changelogs, error messages.

Hard bans:

- No em dashes or double dashes. Use commas, periods, parentheses, or rewrite the sentence.
- No emojis. Anywhere.
- No AI filler vocabulary: delve, utilize, leverage (as a verb), facilitate, streamline, empower, harness, unlock, elevate, seamless, robust (unless naming a literal spec property), crucial, vital, fundamentally.
- No antithetical constructions. No "not X, but Y" and no "it's not just X, it's Y."
- No context-framing preambles. No "In today's fast-paced world," no "It's important to note," no "Without further ado," no "Let's dive in."
- No emphasis bold or italic in prose. Emphasis comes from word choice and sentence structure. Bold is reserved for UI element names inside step instructions (Click **Connect**).

Style:

- Lead with the point. State what a thing does plainly, then add detail.
- Short paragraphs, one to three sentences.
- Vary sentence length. Mix short fragments with longer explanatory sentences.
- Comments explain why, only where the logic is not obvious. Do not narrate obvious code.
- Prefer maker verbs: build, wire up, spin up, ship. Not implement, integrate, instantiate.

### File boundaries

Only create, edit, or delete files inside the current repository. Never touch files outside the project root.

### Quality gates

Nothing gets committed until it passes. Run the test suite, the linter, and the formatter, and confirm all three are clean before any commit.

## Code conventions

### Every language

- Minimal dependencies. Every new crate or package has to earn its place.
- Explicit return types on every public export.
- No commented-out code left in the tree.
- No dead code. No TODO without a reason attached.
- Research the system before building it when the design is not already settled.

### Separation of concerns and modularity

- One module, one responsibility. Name it for what it does, and keep it doing only that.
- Keep core logic framework-agnostic. Business logic does not import the web framework, the transport, or the UI. The shell depends on the core, never the other way around.
- Dependencies flow one direction. No circular dependencies. Lower layers know nothing about the layers above them.
- Modules talk through narrow, explicit public interfaces, not each other's internals.
- Separate side effects (I/O, network, disk) from pure logic so the core stays testable in isolation.
- UI components are headless where it fits: structure and behavior in one place, styling in another.
- Prefer many small focused files over a few large ones. When a file starts doing two jobs, split it.
- Config and feature flags live in one place, not threaded through every module.

### Rust (default stack)

- `cargo fmt` and `cargo clippy` clean before commit. `cargo test` green.
- No `unwrap()` or `expect()` in production paths. Tests and genuinely unreachable cases only.
- `anyhow` for error handling at boundaries.
- Workspace layout: all crates under `crates/`, workspace dependency inheritance.
- Internal-only crates (test utils, soak, conformance) are `publish = false`.
- Edition 2024, Rust 1.85 or newer. Max line width 120.
- Integration tests use real connections (network, disk, hardware) over mocks where feasible. Mocks are a fallback, not the default.
- Feature flags gate platform-specific code.

### TypeScript

- Strict mode. No `any`.
- Explicit return types on all exports.
- Test driven: tests first, then implementation.
- Vue uses Composition API with `<script setup lang="ts">`. No Options API.

## Git conventions

- Conventional commits: `feat(scope):`, `fix(scope):`, `test(scope):`, `docs(scope):`, `chore(scope):`.
- Atomic commits. One logical change each.
- Squash merge to main.
- PRs carry a summary and a test plan.
- The authorship rule above still holds. No exceptions for any of this.

## Design system

Any project with a UI needs a design system in place before interface work spreads across the codebase. Define it once, centralize it, and keep everything downstream consistent with it. The specific look (palette, type, density) is a per-project decision, but the discipline below holds everywhere:

- Single source of truth for design tokens: color, type scale, spacing, radius, shadows, motion. One place, not values scattered across components.
- Theme from those tokens. Support light and dark, and per-instance or per-brand theming where the project calls for it, by swapping token values rather than rewriting components.
- Components consume tokens through `var(--*)`. Zero hardcoded colors, fonts, or spacing in component styles.
- Stay consistent with the system that already exists. Do not introduce one-off values or parallel styles. If something genuinely needs a new token, add it to the central set instead of inlining it.
- Prefix component CSS classes with a short project tag to avoid collisions.
- For any UI: keyboard navigable, ARIA labels on interactive elements, WCAG 2.1 AA minimum contrast and sizing.

## Session logging (optional, recommended for long projects)

After a meaningful work session, write or update `docs/sessions/NNN-description.md` with what was done, decisions made, open questions, and next steps.

## Project-specific

### Metadata

- Author: Moheeb Zara <hackbuildvideo@gmail.com>

- Component CSS class prefix: `jig-`. There is no published npm package; this repo is cloned, not installed.

### Architecture

- Single Nuxt 4 app. Not a monorepo, no workspace packages. The pieces that would have been packages are internal folders.
- `app/` holds the Vue app (pages, layouts, components, middleware, the design layer). `server/` holds the Nitro backend (Drizzle db, better-auth config, API routes). Config sits at the root.
- Dependencies flow one way: pages and components depend on the design tokens and the auth client; the server owns db and auth and exposes them only through API routes. Components never import server code.

### Tech stack (locked)

- Framework: Nuxt 4 (Vue 3, TypeScript strict), Nitro server.
- Database: Postgres via Drizzle ORM, schema as code, drizzle-kit migrations.
- Auth: better-auth mounted on a Nitro catch-all route, backed by the project's own Postgres. Email and password plus GitHub OAuth in v0; passkeys, OAuth providers, and org primitives layer on after.
- Components: Reka UI headless primitives wrapped by thin `app/components/ui/` components that read only from tokens.
- Design system: Tailwind v4 through the Vite plugin. The token contract is a flat set of CSS custom properties (`--color-*`, `--font-*`, spacing, `--radius-block`, `--shadow-block`). Each aesthetic is one file under `app/assets/design/themes/` that redefines those names. Swap with one `data-theme` attribute on `<html>`.

### Testing

- Vitest. `test/unit` for pure logic, `test/components` for component rendering (both via `npm run test`, no infrastructure). `test/e2e` for integration.
- The e2e suite boots the real Nitro server and talks to a real Postgres, no mocks. Run it with a database up: `docker compose up -d db`, then `DATABASE_URL=... BETTER_AUTH_SECRET=... DISABLE_RATE_LIMIT=true npm run test:e2e`. It applies migrations itself, and skips when `DATABASE_URL` is unset so `npm run test` stays infrastructure-free.
- `BETTER_AUTH_SECRET` is required for e2e because it runs a production build, which refuses to boot without one. `DISABLE_RATE_LIMIT` is a test-only escape hatch, never set in production.
- CI (`.github/workflows/ci.yml`) runs lint, typecheck, unit and component tests, build, then e2e against a Postgres service.

### Publishing

- Not published to any registry. Distribution is `git clone`, rename, ship. MIT license travels with it.
